# 有限修复过程v1：冻结合同与数值对照

更新：2026-11-10。本阶段实现`RepairState`、`RepairFeedback`、有限过程与三种人工数值控制。本文件的实验前版本随新研究冻结。尚无离线LLM生成算子或本阶段在线模型试验；后续实验结果另节列出，不据预期填写。

## 问题与评价合同

沿用点功率测量、局部时空GP、已知几何、自定位与定高恒速条件。不更改环境、GP、固定J或能量约束：

`J = ∫[1 + 2 clip((mean_dBm + 80)/10,0,4) + 0.4 clip(std_dB/15,0,2)] ds`。

它是当前快照估计代价，不是未来暴露、设备失效概率或物理剂量。只有完整可行候选且J至少降低1e-7才换路。未来真实场不进入此接受器，也不向任何过程反馈。当前J/估计的局限见[诊断](repair_diagnostics.md)。

分别设立两个验收层：

1. 求解层：同一快照、起始路线、种子和资源上限下，比较最终J、改进幅度、样本/边评价、候选和数值耗时。无可行解单独报告，不能通过抛弃困难任务改善均值。J不升是接受器性质，本身不是方法优势。
2. 任务层：在完整闭环中独立报告到达、航程、超参考秒数、积分、能量和计算耗时。试验前约定一个保守的开发阶段收益门槛：双方所有任务均到达，平均航程和平均暴露积分均不增加，且其中至少一项降低5%，才称本阶段出现任务权衡改进；不通过时仍报告连续数值。该门槛只是开发验收，不是安全条件、统计显著性或最终论文标准。

无新模型调用，不比较模型推理耗时。仿真仍只计0.5s固定决策悬停，真实计算时间不推进场；飞行积分不含悬停，不能据此声称实时部署。

## 状态与反馈

`src/uav_em/repair_process.py`只接收已存在的当前公共上下文与数值规划接口，不导入真值世界。

`RepairState`含合同版本、快照时间、当前路线版本、白名单公共上下文和已经产生的过程反馈。公共上下文仅有车辆任务、已知建筑、最近点测、公开GP样本、当前剩余路线的anchor/逐段代价与支持时效、共享资源。无支持样本均值强制为null，未来点测拒绝。历史兼容源推断、评价配置和任意外部模块不转入合同。算子只使用这些公共字段；规划/复核层仍使用同一完整内部GP，逐段汇总是其派生信息，不是新增传感能力。

区段选择提供`whole/supported_interference/unknown_front/stale/detour/evidence`：

- 已支持干扰按`段干扰代价 / max(段长,1m) × 支持比例`排序；全零时显式记录无区分力，回退未知前沿。
- 未知前沿按`(1-支持比例)/(1+0.25×剩余段序号)`排序，是偏近端的人工启发式，不是信息增益最优。
- 陈旧段按`支持比例 × 支持点平均年龄秒数`排序；无支持不伪造年龄。
- 几何冗余按两相邻边长度减弦长排序；padding为0–3个连接点。
- `evidence`优先有非零已支持干扰的段，其次有几何冗余的段，否则未知前沿。不是通过功率推断真实源方向。

`RepairFeedback`固定字段含候选ID、接受/原因、J分解、当前GP下候选支持/未知/年龄/标准差摘要、重复ID、工作增量与剩余额度、路线版本。明确禁止未来暴露评价字段。状态、原始普通提议、搜索、结构化反馈与实际保留路线都保存。

结果类别区分`improved/no_gain/geometry_failure/search_failure/resource_stop/duplicate/stopped/policy_error`。有解但J不改善，不能解释成没有减少暴露的路线。被拒绝的原始完整候选单独保留；候选去重去除共线插点但保留折返。快捷连接的重复路径可在额外边评价前跳过；RRT重复路径只能在搜索后识别，已耗工作不退回。

## 有限过程与预算

JSON程序最多6节点，每节点为一个预设修复操作及按上述结果类别选择的后继；只允许向后面的节点跳转或停止，因此无循环、任意条件表达式或在线Python。每次重新从当前路线版本解出连接点，不使用已飞航段ID。当前没有LLM生成这种程序，只有人工固定的两份过程。

每决策上限仍为2100个采样提议、10000次边评价，跨区段、双腿、节点、初始求路和终检共用。节点数与旧版最多3轮咨询不是同一概念；本次三组全部最多6次操作，不能据此把新结果与旧3轮LLM直接归因比较。无路时用共享余额求初始路线，单列数值恢复。

固定分配每次最多350样本；反馈分配按最近一次有样本消耗的边/样本增量估计比率（下限16，初始64），将剩余边预算按后续计划搜索节点分摊，每次最多700样本。很少的余额时停止。这里的后续节点数只是保守额度规则，分支可能跳过节点，实际资源未必用满。算子构造与公开摘要也消耗CPU，其时间单独记录，不宣称相同边数等于相同耗时。

## 三个数值对照与冻结顺序

- `library_numeric`：上一版同库规则，通过同一新执行器运行，快捷连接后仅有支持干扰才局部搜索，遇一次有解无改进会停。当前操作上限为6，分配可能与旧3轮版本不同，结果不直接复制历史值。
- `fixed_process`：全段快捷连接→局部→扩区间局部→左侧via→右侧via→全段搜索；每次至多350样本，没有按搜索结果改序。
- `adaptive_process`：使用相同预设构造集合；局部失败后扩区间，有解无改进或重复则换侧向构造，改进后跳到全段搜索；按实际边/样本反馈分配额度。这是更充分的开发对照，不称最强传统算法。

两份过程、合同、源码、快照、场景与预算在运行前保存。4个既有开发快照各3种种子、三方法配对，共36项求解任务；保存所有求解输出后冻结manifest，再事后评估每组最终路线。之后两个既有场景各三方法做闭环，共6项飞行，不挑结果。事后固定路线评分与真实闭环飞行分开报告。

所有既有快照/场景均已看过，只属开发数据。新研究保存前瞻划分：未来新生成城市seed611/613/617/619用于开发，701/709用于验证，1601/1607/1609/1613/1619/1621用于冻结后的测试；本阶段不生成、不读取这些场景或按测试表现改参数。划分是生成任务的保留标识，具体生成器与源分布须在阶段3前共同冻结；仅保留seed并不意味着最终测试协议已经完成。

阶段3可在开发集上离线设计/生成算子，必须记录生成、评价、错误、筛选与模型成本；阶段4再比较同库在线LLM组合。当前人工数值流程不冒充离线模型生成的创新结果，目标权重也不因某个方法失败而事后修改。

单入口`tools/run_process_study.py`，各研究拒绝覆盖，GIF集中于新研究`replay/`。初始工程验证和实际研究结果以运行完成后的报告为准。
